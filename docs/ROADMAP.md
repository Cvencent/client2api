# client2api 0.5 方向说明

本文档决定 0.5 做什么，并给前端的工作排期提供依据。依据只有一份：`CHANGELOG.md` 的 0.4.x 段落与仓库现状，不含对未来平台的猜测。

一句话结论：**0.5 不再加平台，做「请求级可观测性」和「拒绝码分类矩阵」两条，先可观测、后分类。** 发布流程自动化推到 0.6。

## 1. 现状盘点：0.4.x 修了什么

0.4.0 到 0.4.5 一共 13 条记录，按四类归并：

| 类别 | 条目 | 数量 |
|---|---|---|
| 平台适配 | 0.4.0 中转站独立出口代理、0.4.0 ZCode 405/3012（system 数组形状）、0.4.1 中转站单独 User-Agent、0.4.1 账号 `extra_headers` 从未下发、0.4.2 中转站 `responses` 协议、0.4.3 Raccoon `X-Client-Device-ID` | 6 |
| 调度与故障转移 | 0.4.4 请求次数限额规则、0.4.4 WorkBuddy 11158 跨平台转移、0.4.5 11158 正确切换平台、0.4.5 上下文上限同平台裁剪重试 | 4 |
| 面板可观测性 | 0.4.0 模型库分页与客户端筛选、0.4.5 路由测速改测生成速度 | 2 |
| 发布流程 | 0.4.0 Windows 检出下的版本守卫测试 | 1 |

只看 `Fixed`（真正的故障修复）的 7 条：平台适配 3、调度与故障转移 3、面板可观测性 1、发布流程 1。

三个判断：

* **平台适配确实是 0.4.x 的最大一块（6/13）**，而且几乎每一条都是「某个站有一条规定我们没满足」——UA 白名单、system 块形状、`device_id`、`responses` 协议、按站代理。这类工作不会收敛：`clients/` 下已有 21 个模块，每加一个站就多一份这类风险。继续按报障节奏补，就是再用三个版本做同样的事。
* **方向其实已经在被动地转向了。** 0.4.4 和 0.4.5 的 5 条里，4 条属于调度与故障转移，平台适配 0 条。也就是说「从加平台转向稳定性」不是新决策，而是已经发生、只是没写下来——没写下来的后果就是下一轮还得从头讨论。
* **同一个故障修了两次，这是最值得处理的一条信号。** 11158 在 0.4.4 修过一次，0.4.5 又修一次。原因在代码里看得很清楚：「是否在同一平台重试」由 `core.Retryable` 判断，「是否换下一个平台」由 `internal/gateway/server.go` 的 `modelRefusal` 另外判断（还带一条 `FailureOther && 404` 的兜底），两张表各自演进，所以补一处漏另一处。这不是手滑，是结构问题。

还缺一块**定位能力**。0.4.3 的 `device_id` 根因是靠 CDP 抓包加全账号账本比对才挖出来的；0.4.5 的测速口径错误是「显示 1–3 tok/s 而真实 100+ tok/s」这种一眼可见的错，而路由测速从 0.1.73 就在面板上了——错值存在的时间比 0.4.x 长得多。这说明现在发现故障的渠道只有两个：用户报障，或者盯面板时恰好看出数字不对。仓库里没有任何地方回答「这一条请求为什么失败」。

## 2. 三条候选目标

### 目标 A：拒绝码分类矩阵——失败转移不再逐个补

**要解决的用户可见问题**：模型在某平台被拒时，请求要么原样抛 400/500 给客户端，要么卡在链上第一个平台失败，而同一个模型组里另外几个平台其实能服务。用户看到的是一个本可以成功的请求失败了。

**对应 CHANGELOG 里的具体故障**

* 0.4.4 / 0.4.5 连续两个版本修 11158（同一个故障两次）。
* 0.4.5 上下文上限「只报上限不报实测大小」原本直接拒绝整个请求，改为同平台裁剪重试。
* 0.4.0 ZCode 405/3012（system 数组形状）：请求带调用方 system 消息时会拼出第 4 块，触发持续「unusual activity」。修法是把形状改对——分类表一行没动。
* 0.4.1 中转站 UA 的 401：站方按客户端 UA 白名单放行，**根本不是凭据问题**，但 401 在分类表里只有一个含义（凭据失效）。修法同样绕开了分类表。

这两条正是要处理的结构问题：症状看起来是「这个账号坏了」，成因其实是「这个站有一条我们没满足的规定」或「这个模型这个档位不能用」。修的时候都绕开了分类表，所以下一个站出现同样的症状时，一切从头开始。

**成功指标（可判定）**

1. 模型级拒绝的回归用例覆盖 11158 之外**至少 2 类**拒绝码（例如 403 `model blocked`、404 `service info not found`），每条都断言「账号不停车 + 请求切到下一个平台」。
2. 「换账号 / 换平台 / 停车 / 就地裁剪」四类动作收敛成**一张显式表**，`core.Retryable` 与 `modelRefusal` 不再各持一半；用表驱动测试固定每一种 `FailureKind` 的动作，新增 kind 时漏配直接测试失败。
3. 至少 3 个当前只会返回 `core.FailureOther` 的模块接入共享分类路径；面板失败统计里「未分类」占比下降（基线需要先测，见下）。

**实现面**：`internal/core/failure.go`（动作表）、`internal/gateway/server.go` 与 `internal/gateway/dispatch.go`（链路判断）、`clients/*/error.go`、`clients/*/classify.go`（模块侧分类）。

**不做**：不加新平台；不做「自动学习拒绝码」这类需要样本积累的机制；不改对调用方的 HTTP 语义——客户端仍然看到 400/429，只是内部多试一个平台；不把显式指定平台（`cline/xxx`）的请求偷偷换掉，这条现有规则保持。

**可拆成的任务（3 个）**

* A1：建 `FailureKind → 动作` 表，`Retryable` 与 `modelRefusal` 改为读同一张表，补表驱动测试。
* A2：补 2 类新拒绝码的端到端回归用例（模型组内第一个平台拒、第二个平台成功）。
* A3：3 个模块的低价值 `FailureOther` 分类接手，并在 `/v1/status` 暴露未分类失败计数作为基线。

### 目标 B：请求级尝试链——面板能回答「这一条为什么失败」

**要解决的用户可见问题**：一次失败只能看到「最近调用」里孤零零一行，或者去翻运行日志。这个请求切了哪几个平台、每个平台为什么被拒、最后为什么放弃，现在无从回答。诊断一次故障的成本是抓包级别，而不是点开级别。

**对应 CHANGELOG 里的具体故障**

* 0.4.3 Raccoon `device_id`：根因靠 CDP 抓包 + 全账号账本比对才定位。
* 0.4.5 路由测速：面板给出 1–3 tok/s 的错误数字，口径（分母是总耗时还是生成窗口）没写在界面上，错了也看不出来。
* 0.4.0 模型库：八百多行整表一次画完把面板卡死——可观测面本身的承载能力也到边界了。

**成功指标（可判定）**

1. 面板「最近调用」里每一条失败请求可展开，看到它的**全部候选尝试**（平台 / 账号 / 耗时 / 拒绝 kind / 是否就地重试成功），顺序与网关实际下发一致。用固定失败注入用例断言：强制第一个平台 11158、第二个 429、第三个成功，展开后必须正好三行且顺序正确。
2. 每条尝试记录带同一个 **request id**（`internal/gateway/usage.go` 的 `UsageRecord` 现在只有 `Attempt bool`，失败尝试是独立一行，和最终请求无法关联；`SessionID` 只能把同一**会话**的多次请求归到一起，回答不了「这一次请求切了谁」）。面板、运行日志、用量三处要能用同一 id 串起来。调用方自己带的 `X-Conversation-Request-ID` 目前只参与会话标识推导，不能代替网关下发的 id。
3. 面板上每个速度、成功率数字旁边有一行**口径说明**（分母是什么、排队与首字是否计入），与 0.4.5 的「首个内容事件 → 流结束」口径一致。

**实现面**：`internal/gateway/usage.go`、`internal/gateway/logring.go`、`internal/gateway/dispatch.go`（request id 与尝试写入）、`internal/panel/usage.go`、`internal/panel/logs.go`、`internal/panel/overview.go`、`internal/panel/index.html`（展开视图与口径文案）、`internal/alerts`（严重失败顺带进告警）。

**不做**：不接外部监控、OTel、远程上报；不加时序数据库；不做跨天留存分析（近期调用保持有界环形缓冲）；不改「只监听 127.0.0.1、个人自用」的定位。

**可拆成的任务（3 个）**

* B1：`UsageRecord` 加 request id，失败尝试与最终请求同 id，`/panel/api/usage` 返回按 id 分组的结构。
* B2：面板失败请求展开视图 + 每个指标的口径说明（**前端，小v 主接**）。
* B3：失败注入回归用例（三平台两拒绝），钉住尝试链顺序与字段。

**前端（小v）接的活就是 B2 加 B1 的字段契约**：先和 B1 一起定 `/panel/api/usage` 的分组返回结构，再在 `internal/panel/index.html` 做展开视图与口径文案。这是 0.5 唯一一块纯前端的活，其余都在 Go 侧，不需要等后端联调排期。

### 目标 C：发布与回归门禁

**要解决的用户可见问题**：每次发布是五步手工流程（改两处版本号、写 CHANGELOG、打包、抄 SHA256、建 tag 与 Release），漏一步就出现版本号或校验和与实际资产不一致；更贵的是修过的平台故障没有回归用例兜底，同一个故障会复发。

**对应 CHANGELOG 里的具体故障**

* 11158 修了两次（0.4.4、0.4.5）。
* 0.4.0 Windows 检出下 `packaging_test.go` 的版本行正则在 CRLF 工作区必然失败——发布门禁自己在 Windows 上是坏的。
* 0.4.1 到 0.4.5 每个版本的 SHA256 都是手工抄进 CHANGELOG 的。
* 0.4.5 的测速口径缺少稳定断言（提交 67fd4c3 把依赖时钟刻度的速率断言删掉了），说明这类回归目前测不住。

**成功指标（可判定）**

1. `make release-check` 一条命令完成：`cmd/client2api/main.go` 与 `installer/setup/main.go` 版本一致、CHANGELOG 存在该版本段落、安装包产出的 SHA256 与 CHANGELOG 里记录的一致，任一不符即失败。
2. 0.4.x 修过的 7 个故障里至少 5 个有可离线运行的回归用例。

**实现面**：`installer/`、`Makefile`、`.github/workflows/`、`tools/`。

**不做**：不买代码签名证书；不做付费 CI；不把发布改成自动打 tag——发布仍由人工按一次按钮，只是把校验自动化。

**可拆成的任务（3 个）**：C1 版本与 CHANGELOG 一致性门禁；C2 SHA256 回填校验；C3 补 2 个缺失的故障回归用例。

## 3. 优先级建议

**0.5 只做 B 和 A 两条，顺序是 B → A。C 整条推后。**

排序理由：

* **B 排第一，因为它才是「被报障推着走」这个现象的直接原因。** 现在的发现渠道只有用户报障，所以版本节奏天然由外部输入决定。B 做完之后，同类故障能在面板上自己看出来，A 的后续每一项也不必再从抓包开始。
* **A 排第二，因为它是用户能直接感知的失败**，而且改动面全在 `internal/core` 与 `internal/gateway`，不占前端排期，可以和 B 几乎并行——只有 A2 的端到端断言需要 B1 的 request id 才能写得干净，所以 B1 要先落地。
* **C 不排进 0.5，理由是它不解决任何一个用户可见问题**，只降低同类问题复发的概率。C 的价值要等 A、B 把「哪些故障值得回归」这件事定清楚之后才最大——现在补回归用例，补的还是 0.4.x 里已经被反复验证过的那几个，收益有限。

发布节奏建议：0.5.0 收 B，0.5.1 收 A。不合并成一个版本，因为 B 的面板改动需要一轮真实使用才能看出口径说明写得够不够。

**需要先测的基线**：A3 与 B1 都依赖「当前未分类失败占比」这个数，而这个数目前不存在——`/v1/status` 只把 `FailureKind` 用于控制流和提示文案，没有任何聚合。基线作为 B1 的副产物产出，不要为它单独立项。

## 4. 留给后续的

明确不在这轮做，下一轮不再从头讨论：

* **C：发布自动化与全量回归**——推后到 0.6，理由是上面写的「先定清楚什么值得回归」。
* **继续加平台（第 22 个 `clients/` 模块）**——冻结。21 个模块、20+ 路由已经覆盖了个人自用的场景，新增平台带来的是又一份平台适配风险，而不是新能力。要加，也必须先满足 A 的动作表：新模块只填分类表，不改链路。
* **多用户、远程部署、账号体系**——不做，与「个人自用、只监听 127.0.0.1」的定位直接冲突。
* **外部可观测性基建（Prometheus / OTel / 云日志）**——不做，属于新增外部服务与付费基建。
* **面板导航再重做一次**——不做。0.3.9 刚把 11 项压成 4 组，同一件事短期内做第二次收益递减；B2 只加展开视图与口径文案，不动信息架构。
* **模型价格 / 档位数据源扩容**——不做。已有「手动值 > 模块上报 > 官方预设 > models.dev 快照」四层回退，不是当前的痛点。

## 5. 这份文档怎么用

A、B 各自已经拆成 1–3 个任务（A1–A3、B1–B3），可以直接作为 issue 的标题候选。C1–C3 保留在本文档里，等 0.6 讨论时直接提升，不必重写。任何新提出的方向，先对照第 4 节：如果落在「留给后续」里，需要写明它解决的故障对应 CHANGELOG 的哪一条，否则不进版本。
